## 已接受的产品边界

我们交付的是能让用户自己的 agent 使用 agent-comm 网络的本地协作组件，以及把它接入具体宿主的适配。产品需要管理联系人、事项、授权和恢复过程；宿主继续负责其原有的模型、私人记忆与日常对话。

| 部分 | 负责什么 | 边界 |
|---|---|---|
| agent-comm / platform | Agent 身份端点、寻址、加密通信、中继、持久投递与传输状态 | 传输成功不能替代业务同意、执行完成或主人授权 |
| 本地协作组件 | 稳定联系人、端点绑定、事项与方案版本、授权记录、检查、业务事件和恢复 | 由产品维护权威状态，不能仅从模型最近一段对话推断 |
| 宿主适配 | 将宿主指令、相关记忆、受控工具与入站消息接入协作组件 | 先接 Hermes，接口保留接其他宿主的空间 |
| 宿主私人记忆 | 事实、偏好、关系、来源及不确定性 | 不要求统一图谱结构，也不把私人图谱同步给远端 |
| 主人交互入口 | 提出事项、查看进度、处理范围变化、撤销 | 主人自然语言已清楚授权的范围不重复确认 |

### 人物与通讯录

解析链条是“宿主记忆中的人物或别名 → 本地稳定联系人 → 已确认的 agent URN 绑定”。宿主可提供人物线索；产品保存可稳定引用的联系人与绑定，避免每次让模型重新猜测收件人。

- “老王”“王哥”可指向同一个联系人 William；显示名、别名和 agent URN 分开保存。
- 一个人可以绑定多个 agent，并带有私人/工作等角色。联系人不会因为换模型或设备而重新变成陌生人。
- 公钥证明端点身份；此端点是否代表现实中的某个人，来自已确认的绑定来源。
- 对方自报名字、介绍新 agent、声称自己更换账号，先是待核实声明，不能直接覆盖本地映射。
- 熟悉程度与允许披露、允许承诺、允许执行分开；`friend` 或 `trusted` 不构成通用授权。

### 私人记忆与对外内容

协作组件按对象、事项、用途、粒度和有效时间，从宿主获取相关信息或计算后的结论。外部协商使用候选时段、获准材料、允许的行动范围等受限内容。完整日历、私人原因、内部评价和模型推断保留在本地。

只读图查询仍然可能大量泄漏。产品不向对端开放任意图查询，也不把“按联系人导出一个子图”作为充分的隐私边界。信息存在主人的知识库中，也不代表主人有权转发其中的第三方资料。

事实需要来源和时效；偏好用于选择方案；推断保留不确定性。明确授权由独立记录管理。入站提议、对方声称“主人已经同意”、未经双方确认的安排，不能写入长期记忆后变成事实或权限。完成后可向宿主写回带来源的确认结果，写回格式由宿主适配决定。

### Skill、动态状态、工具与恢复

这四部分共同构成可用的集成方式：

1. **Skill** 说明何时解析联系人、建立事项、读取授权、处理入站事件与请求范围变更。
2. **动态状态** 给出当前事项、有效授权、方案版本、待处理决定和已完成动作。Skill 中不能固化这些会变化的数据。
3. **工具** 执行联系人解析、受限查询、提出方案、检查授权、发送及业务动作。真正产生披露或承诺前，由程序读取当前权威记录检查。
4. **恢复** 让刷新、重启或新的 agent 对话能按事项 ID 找回状态，识别已执行动作与未处理事件，并继续原事项。恢复不能靠重复播放旧授权直接再执行一次。

Skill 是使用说明，持久状态是事实依据，工具是执行入口。单独提供一段提示词不足以建立这一边界。真正的宿主集成还需要约束绕过协作工具直接读取、发送或执行的路径。

## 本轮 Demo

### 场景与操作路线

页面入口为 Next.js 的 `/demo`，使用浏览器客户端纯状态机及 `localStorage` 保存演示状态。页面包含“协作事项”“通讯录”“授权与披露”“接入与边界”四个视图，可自动推进或逐步演练。

开始事项前可切换知识图谱、文本笔记和无长期记忆三种示例模式。三种模式使用相同的本地稳定联系人和协作状态结构，不要求迁移记忆。它们只切换示例来源说明与人物引用，不读取真实宿主记忆，也不以不同模型运行来比较记忆效果。

| 步骤 | 演示行为 | 产品含义 |
|---|---|---|
| 发起 | 主人提出与“老王”或“王哥”进行一次 30 分钟技术交流，并交换两份指定资料 | 一次事项委托覆盖正常协调过程 |
| 寻人 | “老王”“王哥”关联到同一个 William 候选；主人模拟核对名片，确认本地稳定联系人到工作 agent URN 的绑定 | 人物、联系人和传输端点分离，名字相似本身不构成身份确认 |
| 准备 | 从本地示例背景得出少量候选时段，选择两份获准资料 | 私人上下文帮助形成结论，对外只给必要内容 |
| 协商 | 按预设对端事件推进方案 | 消息、提议和双方确认具有不同状态 |
| 变化 | 对端提议让陈同学 Chen 加入；Chen 是预设已确认的模拟联系人 | 新提议先记录为待决定事项，不能因 William 提到一个名字就新增可信绑定或权限 |
| 主人决定 | 仅本次允许 Chen 参会并接收最小邀请信息，或保留原来的两人交流 | 只处理新增的决定，不将一次同意变成永久规则；两份资料仍仅给 William |
| 完成 | 每个参与方独立接受同一版 30 分钟安排；三人分支包含 Chen 的独立同意状态 | 我方或 William 的同意均不替代 Chen 的同意，结果绑定参与人、资源和方案版本 |
| 恢复与边界演练 | 刷新恢复；撤销授权、令授权过期、尝试使用旧版本及重复执行 | 恢复后继续读当前状态，失效或旧同意不能继续生效；同一次模拟执行不重复产生结果 |

单次扩权仅覆盖本次参与人变化，以及向 Chen 提供时间、议题、参会名单等最小邀请信息；两份资料的接收者仍只有 William。选择保留两人时，原事项可以继续。等待主人决定期间不向 Chen 模拟披露资料或邀请信息，也不自动批准。

撤销阻止后续行动，不声称收回已经披露的内容。状态机在推进方案及模拟执行时检查当前授权与版本，过期或旧同意不能用来继续执行。模拟日志分别记录事项变化、披露内容、各方同意和执行结果。

### 明确的模拟边界

- 这是客户端产品演示；对端 agent 的回应、双方私人背景、联系人、URN、时段和资料均为示例或预设状态。
- 没有真实模型推理；不把固定回复和状态迁移称为真实 agent 自主协商。
- 不连接真实 Hermes、helper 或 platform，不发送真实消息，不创建真实会议或日历，不向任何人传送文件。
- 页面中可见的“发送”“确认”“完成”表示模拟业务状态，不构成网络送达、对方本人认可或外部工具执行的证据。
- `localStorage` 仅用于演示恢复，既不是生产授权数据库，也不是多设备同步、加密存储或可信的权限隔离设施；用户可以修改本机浏览器数据。
- 如果页面为解释而同时显示双方背景，那是演示可视化，不代表真实部署中一方能读取另一方的私人上下文。
- Demo 不验证真实绑定证明、模型抗提示注入、对端权限执行、崩溃下副作用幂等或跨机器撤销传播；这些留到真实集成阶段验证。

## 后续接入真实 Hermes / helper

以下是接入计划，不属于本轮已完成能力：

1. **提取本地协作内核。** 将 demo 验证的联系人绑定、事项、授权、方案版本和事件迁移变成独立逻辑，并用持久存储维护权威记录。建立当前版本检查、执行前授权检查及业务幂等记录。
2. **定义宿主窄接口。** 让 Hermes 提供相关人物线索、偏好或计算后的候选项；不要求它迁移整张知识图谱。外部声明和确认结果通过不同写回入口处理。用户尚未提供自建图谱的实现细节，应在拿到接口资料后再确定适配。
3. **提供协作 skill 与工具。** Skill 引导 agent 读取当前事项；工具负责解析联系人、建立委托、读取受限上下文、处理提议、申请变更、推进和恢复。授权及事项状态继续由产品持有。
4. **复用 SDK 中的 Hermes connector。** 当前有效路径在 `agent-comm-platform/agent-comm/connectors/hermes-platform/`；根目录 `connectors/` 的旧安装包已退役。保留 helper 的密钥、持久 mailbox、稳定 `message_id` 与 connector receipts。
5. **接入真实业务事件。** 使用已有 `conversation_id`、`task_id`、`in_reply_to` 等字段关联事项；结构化提议、接受、变更及结果由本地协作规则解释。外部 `kind` 或文本不直接获得控制权。
6. **打通主人决定返回执行端。** 对话或 Web 中的批准必须更新本地可检查的授权记录；仅在 Web 写入 `approved` 不构成执行闭环。双方各自验证各自主人的授权。
7. **验证恢复与真实副作用。** 先用两个测试身份和无敏感示例资料验证断线、重放、重复消息、过期、撤销及旧方案；再接日历或文件工具，验证执行前检查、业务幂等、部分失败与补偿。真实用户任务需独立的明确授权范围。

真实消息链路仍为 Hermes Gateway ↔ 本机 helper ↔ agent-comm 网络。Helper 收下消息、网络 ACK、Hermes 处理完成、协作业务完成是不同证据；后续界面与日志应保持这个区分。

## 未决问题

- 本地协作组件最终以独立服务、宿主插件还是两者组合交付？先保持状态与工具接口可分离，不在 demo 阶段锁死部署方式。
- Hermes 现有知识图谱怎样引用人物、记录来源与有效期、接受带来源的写回？未查看用户私有图谱，也未扫描私人机器目录。
- 谁维护人物别名、稳定联系人与 agent 绑定的更新？第一次确认、冲突消歧、密钥轮换和多个角色如何呈现？
- 自然语言委托如何提取为结构化范围，并在实质歧义时请求一个具体决定？哪些模板值得产品化？
- 哪些能力必须通过受控工具，宿主内其他直接发送或读取路径如何限制？Demo 的 UI 状态检查不能回答这个问题。
- 真实 Web 与本地组件如何安全交换主人决定、展示状态并处理离线版本冲突？哪些私人内容需要进入 Web，应另行明确。
- 第一个真实闭环选择真实日历写入，还是先做到双方确认安排并由主人手动落日历？两者的授权与失败处理成本不同。
- 长期授权、多人协作、主动联系、陌生人发现和跨组织转委托暂不作为本轮完成条件；何时引入取决于当前窄场景是否省去双方的实际注意力。
