## 3. 环境、身份和允许的操作

| 层 | 环境 | 本轮用途 | 允许的动作 |
| --- | --- | --- | --- |
| E0 | 本机临时目录和数据库 | 全量组件测试、协议向量、迁移、管理 UI、文档/打包检查 | 自动化读写临时数据 |
| E1 | 本机真实 Platform + 双 helper + Web 测试进程 | 旧 v1 兼容、签名 v2 两模式、跨语言、故障注入 | 临时身份、随机端口、无真实用户数据 |
| E2-L | 阿里云 ECS 上**独立**的 legacy 兼容 staging | 当前新镜像在未启用 v2 策略时的 HTTPS、Web、Hermes/旧包回归 | 测试账户与隔离卷；不得修改生产策略或生产卷 |
| E2-V | 同一 ECS 可承载的**另一套隔离** v2 staging | 策略签发、`private`→`compliance`、管理写操作、迁移和回退 | 独立域名/路由、Compose project、容器名、端口、卷、Platform 身份、密钥及 Web 数据库 |
| E3 | 当前公网生产 | 代码上线后的健康、文档、下载、管理鉴权与只读状态；需要时另用合成 smoke 账户登录 | 默认只读；登录会产生会话/审计写入，须单独记入范围并清理，不签策略、不删除消息、不改变运行参数 |

E2-V 的政策对同一 Platform **全局生效**，不能在现网 Platform 上只给 Alice/Bob 打开 `compliance`。现有 Compose 固定容器名和端口，仓库当前没有可直接使用的 staging override；实际执行前须生成并检查 override，逐项核对路由、卷、密钥和进程隔离，再叠加 v2 覆盖文件。复测安装与双 Agent 时，A/B 各有独立 Hermes profile、Python 环境、helper 密钥、URN、mailbox、SQLite、端口、Web 账户及浏览器会话；第二个 helper 不等于第二个真实 Hermes。迁移测试在**同一套测试身份和数据**上升级，不通过重置身份“修好”问题。

E2-V 使用新生成的测试策略根，离线根私钥不进入容器、镜像、`.env` 或日志；Web 只获得受管签发者用途的密钥，Platform 只获得网关/回执用途的在线密钥。所有策略根、Platform Peer ID 和双方完整身份公钥的固定要有独立核对来源；直接信任 Platform 返回的自我介绍不能证明核对完成。故障注入、删除、清空、配置写入和回滚只在 E1/E2-V 运行。保留原始 v1 队列作为迁移样本，但只用合成消息，绝不复制真实用户数据库作可写 fixture。

候选安装包由发布工具从**干净且已提交的四仓固定检出**构建；当前工作区的文档编辑不能被悄悄打进包。候选包放独立输出目录并明确标注“未公开”，不覆盖现网 `downloads/` 或 GitHub Release。

**已知缺口与本轮进展：** 仓库尚无可直接启动的 E2-V staging override，必须先制作并证明与生产隔离。只读公网核查发现当时公开的[协议说明](../architecture/COMPLIANCE_GATEWAY.md)仍写“尚未发布或部署”、[用户升级说明](../users/PRIVACY_MODE_UPGRADE.md)仍写“仍是工作区源码”；它们与已部署但未启用策略的事实不符。本地文案已修正，但实际发布并复测公网前，T13 仍不能判通过。当前 Web 页面展示已验签模式、epoch、Platform ID 和网关 key ID，`policy_hash` 由 API 返回并在确认请求中绑定，页面没有直接展示哈希；T18 必须分别核对展示内容和后台哈希绑定。若产品要求用户**目视核对精确哈希**，则还须先补界面能力，不能靠自动化代替人的核对。公开 v2 完整包及 macOS 原生环境验收尚不存在；本轮仅完成了未公开 Linux amd64 候选包在一次性 Linux 容器中的原生安装，T20 不得预先标通过。

### v2 必测策略组合

| Platform 策略 | 旧 v1 Agent | 新 v2 Agent | Web 托管控制台 | 不可混淆的结论 |
| --- | --- | --- | --- | --- |
| 无签名策略（当前生产） | 按现有旧路径回归 | 没有可信根时停止普通新发送，不静默伪装已升级 | **仅从未固定 v2 根、也未见过签名策略**的账户走 legacy；已固定/见过策略后遇 404 必须失败关闭 | 只证明兼容运行，不能用 404 降级绕过 |
| 签名 `private, allow_v1=true` | 可继续 v1，但不是 v2 私密握手 | 验签并固定双方公钥后走 v2 私密；无网关槽 | 验签后按允许的兼容路径 | 两类流量分别记账 |
| 签名 `private, allow_v1=false` | 普通 Agent 间 v1 被拒 | 走 v2 私密 | 仅有效托管证书的明确 v1 例外 | Web 例外不是网关合规回执 |
| 签名 `compliance, allow_v1=false` | 普通 Agent 间 v1 被拒 | 各自本机授权该 hash 后方可 v2 收发 | 各账户分别确认披露、有效证书后继续其受管 v1 控制 | Web 确认、A 授权、B 授权是三个事实 |
| 错根、错平台、过期、倒退或不可取得 | 不得作为绕过后门 | 失败关闭、不降级 | 停止新控制/同步；旧副本可读且标明陈旧 | 任何 HTTP 200/ACK 不替代已验签事实 |

## 6. 执行顺序与发布门禁

~~~mermaid
flowchart LR
    F["冻结源码、镜像、策略和公开包清单"] --> U["E0 全量组件/迁移/文档/发布脚本"]
    U --> I["E1 旧 v1 兼容 + 新 v2 双 Agent"]
    I --> L["E2-L 当前兼容模式真实首装与双 Agent 回归"]
    L --> P["E2-V 已签 private 与 Web 受管路径"]
    P --> C["E2-V compliance、双端授权和负向门禁"]
    C --> R["E2-V 旧队列、管理写操作、备份/回退"]
    R --> H["真人理解/决定/模型/移动体验"]
    H --> S["E3 默认只读烟测与报告"]
~~~

1. **每一步先满足前一步门禁。** E0/E1 的 P0 失败就不进入 E2；签名策略未验签、错人或未经授权而成功披露，立即停止 v2 测试并保留证据。E2-V 与生产卷/入口有任何重叠，停止故障注入和配置写入。
2. **当前“代码已上线”补充验收门禁：** T00、T01、旧 v1 T02、T03-L、T04-L、T08-L、T09-L、T11-L、T12 公开 r2、T13～T15 的兼容部署部分、T21-L 通过；E3 默认只读核对后才能说新镜像的**兼容路径**回归完成。T05-L/T06-L/T07-L/T10-L 若未执行，仍标未执行，不称“全项目验收通过”。
3. **启用签名 `private` 前门禁：** T16、T18 的私密/受管分支与 T19 兼容升级、离线告知路径通过；策略根和预期 Platform ID 已通过可信渠道固定，旧客户端支持窗口和失败退出路径明确。现在没有达到这一步，不能把生产 404 当成 v2 测试失败。
4. **启用 `compliance` 或发布 v2 包前门禁：** T16～T20 全部 P0 通过，T05-V/T06-V/T07-V/T10-V 真人环节按声明的产品范围验收；两侧用户能分别拒绝、授权、撤回，旧消息处理窗口、公开告知与包清单准备好。仅有 Codex 对合成账户执行 CLI 属于机制测试，不是两位真实用户已同意；本方案不替代法律审查。
5. **非功能观察：** 并发负载前先固定请求数、并发、时长和基线；本轮目标为无丢失、重复业务、越权、HTTP 5xx、Code 5 或 P2024。p95/p99 和达到 2 秒的轮询用于比较与定位，不在测后随意修改阈值宣称通过。非注入时出现的 TLS EOF 单独记录为失败/待定位；故障注入窗口内的预期断线则按恢复和去重断言判定。重跑成功不改写原失败记录。

## 7. Codex 与你的分工、报告证据

Codex 可准备 E0/E1/E2 隔离环境、构建三类二进制/镜像、生成合成账户与政策、执行自动测试、操作已约定选择的临时 Web UI、施加隔离故障、备份和复读测试数据、收集日志并出报告。测试时的合成 A/B 政策授权可以由 Codex 操作来验证机制，但必须标为“脚本模拟授权”。需要你本人参与的是：核对真实身份/策略根的带外来源与披露含义、Alice/Bob 各自的真实本机许可或拒绝、Web 告知是否易懂、T05/T06/T07/T10 的真人理解和决定，以及任何正式生产政策切换/公开包发布决定。一个人可轮流扮演 A/B，但证据必须说明是同一测试者的两次独立决定。

每个 RUN_ID 保存 `versions.json`（四仓提交、镜像、活动政策 hash/epoch/mode、公开包 manifest）、`matrix.json`（用例、环境、PASS/FAIL/未执行/受阻、执行者）、请求/消息/审批与回执的去敏时间线、浏览器/原生会话截图、容器和 Agent 日志索引、SQLite 备份校验与最终 `result.json`、`cleanup.json`。密钥、凭据、真实数据库、正文和完整私人日志只留在受限临时位置，不进 Git。每条结论标明是**源码单测、本地进程、隔离 staging、真人体验还是线上只读**；`submitted`、MQ ACK、网关准入回执、收件持久化、用户决定和任务完成分别取证。

本轮最终交付一张带证据路径的 T00～T21 结果表、已知问题/未覆盖项和三项单独结论：① 当前兼容代码是否通过；② 隔离 v2 私密/合规模式是否通过；③ 公开安装包是否包含并通过对应能力。任一项没有实际运行证据时明确写“未执行”，不借其他层的通过结果补齐。
